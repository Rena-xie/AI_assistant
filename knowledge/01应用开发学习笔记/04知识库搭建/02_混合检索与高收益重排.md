检索与存储是 RAG（检索增强生成）系统的“记忆库”与“寻路机制”。传统的单一向量相似度检索在真实业务场景中极易退化，工业界目前的标准解法是构建**混合检索（Hybrid Search） + 重排序（Reranking）**。

## 一、 向量化（Embedding）底座

向量化是将自然语言转化为计算机可计算的高维数学空间的过程：

- **物理指标核心概念**：
    - **向量维度（Dimension）**：表示语义空间的复杂度（如 768 维、1536 维等）。
    - **余弦相似度（Cosine Similarity）**：计算两个向量在高维空间夹角的余弦值，用以评估语义相关性。
    - **欧氏距离（Euclidean Distance）**：计算高维空间中两个点之间的绝对几何距离。
- **主流 Embedding 模型选型**：
    - _国内主流_：BGE（北京人工智能研究院）、M3E、Qwen Embedding（阿里通义、智谱 GLM 等商业及开源 API）。
    - _国外主流_：OpenAI text-embedding-3 系列、Cohere Embed。

## 二、 向量数据库与存储架构

向量数据库不仅存储数据，更负责对千万级数据执行高并发的毫秒级检索：

### 1. 核心物理概念

- **向量索引**：用于加速高维向量匹配的数据结构（如 HNSW 索引等）。
- **ANN 近似最近邻搜索**：在高维空间中，牺牲极小比例的精度换取检索速度提升，是毫秒级查询的物理支撑。
- **Metadata 过滤**：允许在向量相似度计算前或计算后，根据附加的业务标签进行硬性过滤。
- **数据分区（Partitioning）**：在大规模数据存储中，将数据逻辑或物理分区，缩小检索范围以提高查询性能。
- **权限隔离**：支持多租户与多业务线的数据安全隔离。
- **存储三要素**：数据库在存储切片时，单条记录必须完整绑定“**知识文本（Raw Text） + 语义向量（Embedding Vector） + 元数据（Metadata）**”。

### 2. 企业常用数据库选型

- **开源/自部署**：
    - **Qdrant**：基于 Rust 编写，内存占用极低，检索性能优异，原生支持混合检索与 Metadata 复杂过滤。
    - **Milvus**：专门针对亿级以上大规模向量、高并发分布式场景打造，支持高度扩展，大型企业首选。
    - **pgvector**：PostgreSQL 的向量插件。最适合已有 PostgreSQL 关系数据库的中小团队，无需引入新组件，运维低开销，轻量、即插即用。
    - **Weaviate / Chroma**：Chroma 适合本地轻量测试；Weaviate 支持图、向量与全文混合检索。
- **商业/云服务（SaaS）**：
    - **Pinecone**：云原生免运维的首选 SaaS，拥有极佳的弹性缩容与极简开发体验。
    - **Elasticsearch Vector / OpenSearch**：传统全文检索大厂的向量化方案，非常适合已有 ES 搜索架构的企业升级接入。

## 三、 用户问题处理（Query Processing）

用户直接输入的原始提问往往存在口语化、意图模糊、信息缺失等缺点。在进行向量检索前，必须对其进行优化：

- **Query Rewrite（查询重写）**：利用大模型将用户提问重构成多条表达更清晰、语义更完整的检索语句，彻底规避口语化干扰。
- **Query Expansion（查询扩展）**：提取或增加提问中的同义词、近义词或相关概念，拓宽检索召回边界。
- **HyDE（Hypothetical Document Embeddings，假设文档嵌入）**：让大模型根据提问先生成一篇“假设性回答文档”，然后利用这篇假文档的 Embedding 去数据库检索真实文档。该技术能完美缩减“用户问题空间”与“文档解答空间”的语义鸿沟，极大拉升 Recall 指标。

## 四、 检索范式：混合检索与重排序

### 1. 基础相似度搜索

用户提问 $\rightarrow$ 优化后输入 $\rightarrow$ 通过 Embedding 转化为向量 $\rightarrow$ 向量数据库计算余弦相似度等指标进行 ANN 搜索 $\rightarrow$ 返回 Top K 个最相似的 Chunks。

### 2. 混合检索（Hybrid Search）

单一的语义向量相似度搜索在专有名词（如特定的产品型号、人名、代码函数名）检索上容易失准。工业级高精度方案必须使用**混合检索（Hybrid Search）**：

- **第一路**：向量数据库运行高维向量相似度检索，捕捉深层语义相似的 Chunk。
- **第二路**：传统搜索引擎（如 Elasticsearch、OpenSearch 或 Milvus Hybrid Search）运行 BM25 全文检索，捕获高精准关键词匹配。

### 3. 重排序（Reranking）—— 提质最明显的环节

混合检索返回的 Top 100 候选 Chunks，在语义相似评分与 BM25 全文检索评分上无法直接拉通对比，且多路召回可能含有较多噪声。

- **运行机制**： 将双路检索到的 100 个候选 Chunks 与用户原始 Query 一起送入强交互的**重排序模型（Reranker）**。重排模型会对每一对 [Query, Chunk] 执行深度的逐字语义交叉比对，无情过滤冗余，重新计算出相关性得分，输出最终最精准的 Top 5 最佳片段喂给大模型。
- **重排模型推荐**：
    - _商业标杆 API_：**Cohere Rerank**。
    - _开源及本地 CPU 极简方案_：**BGE Reranker**、**Jina Reranker**、**FlashRank**。
痛点：纯向量检索对代码函数名（如 from\_tiktoken\_encoder）、配置项参数等精准关键词极不敏感。

工程实现：构建 BM25 关键词检索 + 向量语义检索 的混合检索管道（Hybrid Search），并引入重排序模型（如 bge-reranker-large）对召回的前 20 条结果重新打分，取 Top 3~5 送入 LLM。

### 2. 混合检索与重排序（Hybrid Search + Reranking）
*   **痛点**：大模型对特定的代码函数名（如 `from_tiktoken_encoder`）或配置参数极其不敏感，纯向量检索经常由于语义稀释而无法召回。
*   **工程实现**：
    *   构建**双路召回管道**：结合基于词频精确匹配的 **BM25 关键词检索** 与基于语义理解的 **Vector 向量检索**。
    *   使用 **RRF（倒数排名融合）算法** 合并两路召回结果。
    *   引入重排序模型（如 `bge-reranker-large`）对召回的前 20 条结果重新打分，仅筛选出高置信度的 Top 3~5 喂入大模型，完美解决大模型的“中间丢失（Lost in the Middle）”问题。
混合检索与重排序 (Hybrid Search & Reranking)
* **单语义向量检索痛点**：对代码函数名（如 from_tiktoken_encoder）、配置项参数及专有名词词频极其不敏感，容易因语义稀释导致召回失败。
* **混合检索架构**：
  1. **双路召回**：基于词频精确匹配的 BM25 稀疏检索 + 基于语义稠密向量的 Dense Vector 检索。
  2. **多路融合算法**：应用 RRF (Reciprocal Rank Fusion，倒数排名融合) 算法对两路召回的前 20 条结果进行融合。
  3. **重排序 (Reranking)**：引入交叉编码器模型（如 bge-reranker-large）对 Top-20 结果进行二次精细打分，筛选置信度最高的前 3~5 条送入大模型，解决大模型“Lost in the Middle（中间丢失）”问题。
### 3. 异步高并发后端与精准溯源（Engineering & Citations）
*   **工程实现**：
    *   基于 `FastAPI` + `asyncio` 搭建高性能异步后端，使用 `StreamingResponse` 暴露 `SSE`（Server-Sent Events）流式打字机接口。
    *   在文档清洗阶段对每个切片深度打标（包含 `source`、`chapter`、`page` 等元数据）。
    *   在大模型吐出回答时，利用 Pydantic 强约束其在回答末尾或句中自动标注精确的页码和来源出处（如 `[Chapter 3, Page 105]`），实现页码级的精准可视化溯源。
生产级后端 API 与精准溯源 (Engineering & Citations)
* **高性能异步后端**：基于 FastAPI + asyncio 搭建高并发响应服务，采用 Pydantic v2 进行强类型数据校验。
* **打字机流式交互**：借助 StreamingResponse 暴露 SSE (Server-Sent Events) 接口，实现低首 Token 延迟流式推送。
* **精准元数据与安全防护**：
  * 在切片阶段打入 source、chapter、page 等深度 Metadata。
  * Prompt 模板中使用 `<context>` 与 `<question>` XML 标签隔离系统上下文与外部输入，防护 Prompt Injection。
  * 大模型生成回答时解析命中元数据，自动在末尾或文中生成可视化精准引用角标（如 [Chapter 3, Page 105]）。
### 4. 量化评估与数据闭环（RAG Evaluation）
*   **工程实现**：
    *   引入 `Ragas` 评估框架，构建技术文档的黄金测试集（Golden Dataset）。
    *   通过大模型作为裁判，生成并量化追踪 RAG 系统的四项核心黄金指标：**忠实度（Faithfulness）**、**答案相关性（Answer Relevance）**、**上下文召回率（Context Recall）**、**上下文精确度（Context Precision）**。
    *   用量化数据（如“加入 Reranker 后召回率从 62% 提升至 89%”）向面试官有力证明你的优化成效。
 量化评估与数据闭环 (RAG Evaluation)
* **评估框架**：引入 Ragas 或 TruLens 自动化评估框架。
* **Golden Dataset 构建**：基于技术书籍构建 30+ 包含真实 Ground Truth 的黄金测试集。
* **四大黄金量化指标**：
  1. **忠实度 (Faithfulness)**：评估生成的回答是否完全忠实于检索到的上下文（防止幻觉）。
  2. **答案相关性 (Answer Relevance)**：评估回答是否精准切中用户提问。
  3. **上下文召回率 (Context Recall)**：评估检索系统是否完整召回解决问题所需的全部证据。
  4. **上下文精确度 (Context Precision)**：评估检索结果中相关信息的密集程度与排序合理性。

## 五、 企业级权限管理

在企业落地中，RAG 必须符合严密的数据安全合规。权限管理的技术流转为： 用户身份（IAM/OIDC） $\rightarrow$ 权限系统解析其访问角色（RBAC 基于角色的控制） $\rightarrow$ 自动拼接权限元数据过滤条件（Metadata Filter） $\rightarrow$ 数据库执行底层过滤检索 $\rightarrow$ 仅返回该用户有权查阅的知识切片。

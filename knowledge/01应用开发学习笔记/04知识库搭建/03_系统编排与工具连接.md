这些文档作为上下文和输入的原始提示词组合，送给文本生成器得到最终的输出。

- **工具注册**：在 API 请求中注入开发者定义的工具列表（使用 JSON Schema 描述函数名、入参类型与用途）。
    
- **意图识别与参数提取**：LLM 识别到需要调用工具，主动停止生成普通文本，转而输出符合 JSON Schema 的调用指令（例如：`{"name": "query_db", "args": {"user_id": 1024}}`）。
    
- **外部执行**：你的 Python/Node.js 后端捕获该 JSON，在本地安全沙箱或服务中执行真实的数据库查询或 API 请求。
    
- **结果回填（Observation）**：将工具执行的真实结果作为新的 Prompt 上下文喂回 LLM，由 LLM 进行二次整合并输出最终自然语言。

在搭建企业级 RAG 系统时，工程难点通常不是“能不能跑通”，而是“如何评测检索与生成的准确率（Evals）”。现实场景中经常面临**冷启动（没有真实用户历史提问数据）**的困境。此时，利用能力极强的 LLM（如 GPT-4o、Claude 3.5）反向批量生成** [Question, Answer, Context] 三元组**，是行业标注的标准打法。

**合成数据集生成 Pipeline**

1. **文档切块（Chunking）**：将知识库文档按规则切分为不同的语义片段（Chunks）。
    
2. **多视角反向提问**：将 Chunk 喂给强大模型，使用 Prompt 引导其模仿不同角色的真实用户，生成多种形态的问题：
    
    - _具体事实题_：“基于这段文本，公司报销餐补的上限是多少？”
        
    - _模糊意图题_：“在公司发票抬头填什么？”
        
    - _跨段落推理题_：“比较甲项目与乙项目的交付周期差异。”
        
3. **提取 Ground Truth（标准答案）**：强迫 LLM 仅根据该 Chunk 的内容，给出 100% 对应的标准答案。
    
4. **质量过滤（LLM-as-a-Judge）**：用另一个 LLM 节点对生成的 QA 对进行评估，剔除含糊不清、过于简单或偏离原文的劣质数据。

系统编排与工具连接负责将前面处理完毕的 Ingestion（文档解析）、Retrieval（检索重排）与 LLM 调用、外部系统 API 整合，构建起端到端的自动化应用链路。

## 一、 RAG 系统上下文组合生成流

在普通的 RAG 调用中，系统编排执行以下经典的闭环链路： 用户提问 $\rightarrow$ 检索系统定位 Top K 精准切片 $\rightarrow$ 编排框架将这些 Chunks 作为事实引文与原始系统指令（System Prompt）拼接为一整段 Context $\rightarrow$ 送入文本生成大模型（LLM） $\rightarrow$ 约束大模型获得最终无幻觉的确定性输出。

## 二、 编排框架选型

### 1. 代码优先框架（Code-First）

- **LlamaIndex**：RAG 领域的绝对霸主。拥有全行业最丰富的索引策略（Index Strategies）、数据图谱连接方式、元数据组织结构以及检索调优接口，最适合对检索路径有极致深度定制要求的团队。
- **LangChain / LangGraph**：AI 开发领域生态最大的框架。当系统由于业务复杂度上升，需要从“单次被动检索”演进到包含多轮推理、反思、自纠错的 **Agentic RAG（多步循环检索）** 阶段时，利用 LangGraph 编写基于状态机（State Graph）的代码级精细编排是绝对的行业主流。

### 2. 低代码可视化平台（Low-Code）

- **Dify**：将知识库自动导入、混合检索、Rerank 跨路配置、大模型调用以及可视化工作流（Workflow）拓扑一站式极简化完美集成。非常适合企业极速跑通 MVP，无缝发布为标准 WebApp 或商业化交付 API。
- **FastGPT**：国内本地私有化部署、高并发企业客服与知识库高频选型平台。

## 三、 Function Calling（函数调用）机制

当大模型本身由于知识库盲区，需要实时去查外部数据库、执行计算、或调用 ERP 等业务接口时，系统通过 **Function Calling（函数调用）** 达成与外部物理世界的连接：

```
                1. 注入 [工具 JSON Schema]
                    ┌─────────────────┐
                    │  LLM 推理内核    │ ◄───┐
                    └────────┬────────┘     │
        2. 主动停止文本       │              │ 4. 结果回填 (Observation)
        输出 JSON 指令        ▼              │
                    ┌─────────────────┐     │
                    │  Python/Node.js │ ────┘
                    │  后端执行沙箱   │
                    └─────────────────┘
                    3. 执行外部 API/数据库
```

1. **工具注册（Tool Registration）**：在向大模型发起 API 请求时，在参数中注入开发者定义的工具列表。每个工具均采用标准的 **JSON Schema** 描述，详细规定函数名称、入参参数类型、具体字段、必填项以及该函数在什么场景下被使用。
2. **意图识别与参数提取**：大模型（LLM）阅读上下文与工具描述。一旦识别到需要调用工具才能完成用户请求，它会**主动停止生成普通自然语言**，转而生成并输出一段符合 JSON Schema 规范的调用指令（例如：`{"name": "query_db", "args": {"user_id": 1024}}`）。
3. **外部执行**：开发者的 Python/Node.js 后端服务捕获该 JSON 代码。在本地安全沙箱或内网服务器中，调用真正的数据库、运行真实的 Python 脚本、或发起外部 API 请求，获取真实的数据。
4. **结果回填（Observation）**：后端将工具执行返回的真实文本结果（Observation）打包，拼接为新的 Prompt 上下文重新喂回大模型，由大模型进行二次整合推理，最终输出可信赖的自然语言给用户。

## 四、 自动推理并使用工具（ART）工作原理

自动推理并使用工具（ART, Automatic Reasoning and Tool-use）是针对 Function Calling 的高阶调度机制：

- **多步推理示范匹配**：当系统接收到一个全新的复杂任务时，首先在预设的**任务示范库**中，匹配并选择与该任务最相近的“多步推理与工具使用”的 Few-Shot 示范，加载至大模型的 System Prompt。
- **生成暂停与恢复机制**：在具体测试和执行阶段，当大模型生成的下一个 Step 遇到需要调用外部工具时，编排程序会**立刻暂停大模型的文本生成过程**，转而执行外部接口，将外部工具的返回结果（Observation）拼接合入当前的生成轨迹后，**唤醒并继续接着生成**后续的内容，直到完成所有多步推导。

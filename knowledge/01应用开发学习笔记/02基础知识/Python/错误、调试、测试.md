### 二、 AI 工程必掌握的三大异常处理设计模式

#### 1. LLM JSON 结构化输出解析与自我修正（Self-Correction）

当大模型未按规范输出合法 JSON 时，利用异常捕获拦截解析错误，并将错误上下文回传给大模型进行纠错：

```
import json
import logging

class OutputParsingError(Exception):
    """LLM 输出解析异常"""
    pass

def parse_agent_action(raw_llm_response: str) -> dict:
    try:
        # 尝试解析 LLM 响应
        return json.loads(raw_llm_response)
    except (json.JSONDecodeError, TypeError) as e:
        logging.warning(f"⚠️ LLM 输出非法 JSON 格式: {raw_llm_response}")
        # 将原始报错包装抛出，交由上层 Agent 触发重试逻辑（Prompt 中带上错误信息）
        raise OutputParsingError(
            f"无法解析您的响应为 JSON，格式错误原因: {str(e)}。请重新输出符合标准的 JSON。"
        ) from e
```

#### 2. Agent 动态工具执行隔离（Tool Execution Guard）

在 Agent 自动化调用第三方 API 或代码工具时，必须做全局异常隔离，防止单个工具崩溃导致整个 Agent 状态机挂掉：

```
import logging

def safe_tool_executor(tool_func, tool_input: str) -> str:
    try:
        # 执行工具方法
        return tool_func(tool_input)
    except Exception as e:
        # 捕获所有工具执行期的未知异常，阻止崩溃向上蔓延
        logging.exception(f"❌ 工具 {tool_func.__name__} 执行时崩溃:")
        # 将错误信息转化为自然语言，直接返还给 Agent 大脑，让其尝试其他工具
        return f"工具执行失败，错误详情: {type(e).__name__}: {str(e)}。请检查参数或更换其他工具。"
```

#### 3. 指数退避重试与降级

处理大模型 API 频率限制（Rate Limit）与网络波动：

```
import time
import logging

class LLMServiceUnavailable(Exception):
    pass

def call_llm_with_fallback(prompt: str, max_retries: int = 3) -> str:
    for attempt in range(max_retries):
        try:
            # 模拟请求 OpenAI API
            if attempt < 2:
                raise TimeoutError("API 网关响应超时")
            return f"成功返回: {prompt}"
        except (TimeoutError, ConnectionError) as e:
            wait_time = 2 ** attempt  # 指数退避 1s, 2s, 4s...
            logging.warning(f"⚠️ API 请求超时 (第 {attempt + 1} 次)，{wait_time}s 后重试...")
            time.sleep(wait_time)
        else:
            print("请求成功")
        finally:
            print(f"--- 记录尝试次数: {attempt + 1} ---")
            
    # 主模型连续失败，抛出自定义异常触发本地小模型降级 (Fallback)
    raise LLMServiceUnavailable("主模型服务不可用，触发降级机制")
```

### 一、 核心知识点与 AI 应用场景

- **`logging` 日志模块（核心重中之重）**
    
    - **需掌握内容**：理解日志级别（DEBUG / INFO / WARNING / ERROR / CRITICAL）划分、控制台与文件输出配置、日志格式化（包含时间戳、模块名、行号）。
        
    - **AI 工程应用**：彻底替代 `print`。在生产环境中记录大模型 API 调用耗时、Token 消耗统计、RAG 向量检索相似度得分、Agent 节点状态迁移以及工具（Tools）入参出参。结合 LangSmith、OpenTelemetry 等 AI 可观测性平台，`logging` 是日志落盘与排查的底层依赖。
        
- **`assert`（断言机制）**
    
    - **需掌握内容**：掌握 `assert 条件, "错误提示"` 的语法逻辑，理解断言失败会抛出 `AssertionError`，以及生产环境可通过 `python -O` 参数关闭断言的特性。
        
    - **AI 工程应用**：数据管道与 Prompt 模板的防御性校验。例如在发送 API 请求前断言 Prompt 变量非空、断言生成出的 Embedding 向量维度满足特定长度（如 1536 维）、断言 LLM 提取出的 JSON 字段包含核心主键。
        
- **`pdb` 与 `breakpoint()` 命令行调试**
    
    - **需掌握内容**：掌握内置调试器命令：`n`（单步执行）、`s`（进入函数）、`p 变量名`（打印变量）、`c`（继续运行直到下一断点）、`q`（退出调试）。掌握 Python 3.7+ 原生 `breakpoint()` 函数的埋点方式。
        
    - **AI 工程应用**：在云端服务器环境、远程 Docker 容器内、或者无 GUI 界面（Headless）的环境下排查 Agent 或向量数据库卡死问题。
        
- **图形化调试器（VS Code / PyCharm Debugger）**
    
    - **需掌握内容**：设置普通断点、条件断点（Conditional Breakpoints）、单步跳过/跳入、查看 Call Stack（调用栈）、Watch（监视变量）变化。
        
    - **AI 工程应用**：单步跟踪 LangChain、LlamaIndex 或 CrewAI 等第三方框架的内部源码调用链，排查复杂 Agent 状态对象（State）在循环逻辑中的异常变更。
        
- **`print` 调试的局限性**
    
    - **需掌握内容**：理解为什么 `print` 只能作为临时脚本的简易调试手段。
        
    - **AI 工程应用**：`print` 无法区分日志级别，会导致控制台日志污染，无法持久化存盘，且多线程/异步（`asyncio`）并发请求大模型时输出顺序会紊乱。
        


| **调试维度** | **传统 Web / 软件开发** | **AI 应用工程 (LLM / Agent / RAG)**           |
| -------- | ----------------- | ----------------------------------------- |
| **调试对象** | 确定的代码逻辑、数据库 SQL   | 动态 Prompt 响应、非确定性 JSON 输出、Embedding 相似度   |

AI 应用的非确定性决定了我们**不能通过单元测试直接验证大模型的生成文采**，但必须通过单元测试对**代码的骨架逻辑、数据清洗、Prompt 组装、JSON 解析器以及工具调用**进行 100% 确定性的防御。

### 一、单元测试

- **测试用例编写规范**：继承 `unittest.TestCase` 类，测试方法必须以 `test_` 开头，以便测试执行器（Test Runner）自动识别并运行。
    
- **断言机制（Assertions）**：掌握常用的断言方法，例如判断值相等的 `assertEqual()`、判断布尔值的 `assertTrue()` / `assertFalse()`，以及测试是否正确抛出预期异常的 `assertRaises()`。
    
- **固件钩子（`setUp` 与 `tearDown`）**：掌握测试前的初始化与测试后的清理工作。`setUp()` 会在**每个**测试方法执行前运行（用于初始化测试数据、Mock 客户端），`tearDown()` 会在每个测试方法执行后运行（用于销毁临时文件、释放内存或数据库 Session）。
    

### 二、 💡 AI 应用工程师的核心突破点：Mock 机制（模拟 API）

在 AI 工程中，单元测试最忌讳**直接发起真实的大模型 API 请求**（会导致测试耗时极长、按 Token 产生费用，且因网络或 API 波动导致 CI/CD 构建随机失败）。因此必须精通 **`unittest.mock` 模块**。

- **API Mocking（虚拟响应）**：使用 `unittest.mock.patch` 或 `MagicMock` 截断对 OpenAI、Anthropic 或自建 LLM 服务的网络请求，模拟返回固定的 JSON 响应或 Token 流。
    
- **异常模拟（Failure Injection）**：利用 Mock 强制触发 API 429（Rate Limit）、500 错误或网络超时，测试系统的指数退避重试逻辑是否正确执行。
    

### 三、 AI 应用开发中的四大真实单元测试场景

#### 1. RAG 文本切块与向量化前处理测试

- **测试重点**：针对边界条件进行确定性断言。
    
- **测试用例**：传入超长文本、空文本、特殊标点符号或跨语言混合文本，测试切块函数是否按预期的 `chunk_size` 和 `chunk_overlap` 切分，确保切片重叠逻辑不丢失关键信息。

#### 2. Prompt 模板渲染与变量注入测试

- **测试重点**：验证复杂系统 Prompt 的组装结果。
    
- **测试用例**：测试传入缺失参数、特殊字符注入（如包含 SQL 或恶意 Prompt 注入指令）时，Prompt 模板类是否进行了正确的安全过滤与变量格式化。

#### 3. LLM 结构化输出（JSON / Pydantic）解析测试

- **测试重点**：验证解析器的鲁棒性。
    
- **测试用例**：通过 Mock 注入各种“瑕疵 JSON”（如包含 markdown 标记的 ```json 代码块、字段缺失、数据类型不符），测试自定义的 JSON Parser 或 Pydantic 校验器是否能正确解析，或是否按预期抛出 `OutputParsingError`。
    

#### 4. Agent Tool（工具）独立单元测试

- **测试重点**：Agent 调用的每一个外部 API 或本地函数必须能够单独测试。
    
- **测试用例**：在不启动整个大模型 Agent 状态机的情况下，直接测试天气查询工具、数据库检索工具、计算器工具在各种入参下的返回值是否符合 Agent 预期的标准 Dict / JSON 格式。
    

### 四、 从 `unittest` 到现代 AI 工程的 `pytest`

虽然廖雪峰教程以标准库 `unittest` 为主，但在实际 AI 团队和主流开源框架（如 LangChain、LlamaIndex、AutoGPT）中，**`pytest` 已成为事实上的行业标准**。

建议在掌握 `unittest` 思想后，进一步了解 `pytest` 的优势：

- **更简洁的断言**：无需调用 `self.assertEqual()`，直接使用 Python 原生的 `assert a == b` 即可。
    
- **参数化测试（`@pytest.mark.parametrize`）**：在 AI 测试中，可以用同一套测试逻辑快速跑数十组不同的 Prompt 输入与预期输出映射表。
    
- **强大的 Fixture 机制**：替代 `setUp/tearDown`，实现更高复用度的测试上下文依赖注入。

对于 **AI 应用开发工程师** 而言，`doctest` 属于**轻量级辅助工具**。在 AI 框架（如 LangChain、LlamaIndex）和大模型 Function Calling 体系中，函数的 Docstring（文档注释）会被直接作为 Prompt 的一部分喂给大模型。`doctest` 的核心价值在于确保这些**写给大模型和开发者看示例代码 100% 准确且可运行**。

### 一、 文档测试

- **交互式示例格式**：在函数的 Docstring 中，使用类似 Python 交互命令行（`>>>`）的格式写下输入参数与预期输出结果。
    
- **自动化提取与执行**：通过 `doctest.testmod()` 模块，程序会自动扫描文档注释中的 `>>>` 标记，提取代码并执行，对比实际结果与注释中的输出。
    
- **严格的文本匹配机制**：`doctest` 采用的是严格的字符串匹配。包含额外的空格、换行符、标点差异或字典 Key 的显示顺序不一致，都会导致测试失败。
    

### 二、 AI 工程真实落地场景

- **Agent 工具（Tools）与 Function Calling 的 Docstring 防腐**：
    
    - 大模型决定调用哪个工具、传入什么格式参数，极大程度上取决于工具函数的 Docstring 描述及 Example。
        
    - 如果代码经过重构修改了入参格式，但 Docstring 里的示例没有更新，LLM 就会根据旧示例生成错误的 JSON 调用指令。
        
    - 使用 `doctest` 可以保证只要修改了代码逻辑，注释中的示例若未更新就会在构建阶段直接报错，防止出现“文档与代码不一致”导致 Agent 运行挂掉。
        
- **纯函数式工具库（Text Processing Utilities）**：
    
    - 在 RAG 和 Prompt 工程中，存在大量文本清洗函数（如过滤 Markdown 标签、提取 JSON 子串、计算 Token 大致数量、Prompt 占位符替换）。
        
    - 将这些基础工具函数的简单使用示例写在 Docstring 中，既作为使用说明，又通过 `doctest` 完成了轻量级单元测试。

### 三、 AI 应用中的局限性与避坑指南

- **无法应对 LLM 输出的非确定性**：大模型每次生成的文本或 Token 序列存在随机性（如不同的词汇表达），而 `doctest` 要求精确的字符比对，因此**严禁**直接将 LLM API 的生成结果写入 doctest。
    
- **不适合异步（`asyncio`）与网络 API**：AI 应用中的网络请求（如 OpenAI API 调用、向量数据库检索）耗时长、包含敏感 API Key，且存在网络波动，不适合放入 Docstring 中作为静态文档测试。
    
- **与主流测试框架的关系**：在实际 AI 项目中，90% 以上的自动化测试工作由 `pytest` 完成；`doctest` 仅作为工具函数和 SDK 自带文档的辅助校验。

在设计 AI 系统时，首要任务是识别任务的复杂度和不确定性，从而在确定性的工作流与自适应的智能体之间做出准确的架构抉择。

## 一、 特征与场景对比

### 工作流 (Workflow)
#### 核心特征
* 预定义的步骤和执行路径
* 高可预测性和可控性
* 明确的任务边界
* 明确的编排逻辑

#### 适合场景
* 定义明确的任务，具有清晰的要求
* 需要可预测性和一致性的场景
* 需要你对执行流程进行明确控制的任务
* 对可靠性要求极高的生产系统

### 智能体 (Agent)
#### 核心特征
* 动态决策机制
* 自主工具选择与使用
* 推理和思考的能力
* 自主执行任务

#### 适合场景
* 具有多种执行路径的开放式任务
* 步骤数量难以提前确定的复杂情况
* 需要适应性推理的任务
* 灵活性比可预测性更重要的情境下

## 二、 工作流三大核心控制模式

在工作流编排中，通常通过以下三种经典设计模式来构建确定性的流控制：

* **提示链 (Prompt Chaining)**：将任务拆解为多步顺序验证，上一步的输出直接作为下一步的输入。常用于内容生成流程、多阶段文档处理和顺序验证工作流程。
* **路由模式 (Routing)**：基于规则或轻量 LLM 的意图识别，将输入分发给最合适、成本最低的专用模型或节点，实现资源的优化调度与智能查询分发。
* **并行模式 (Parallelization)**：同时激活多个独立的节点处理任务，最后由聚合节点进行汇总整理。
  * *典型场景*：内容审核系统、多标准评估、同时性数据处理、独立验证任务。
  * *工程优势*：能够极大降低多步链条的累计延迟，更好地利用资源并提升系统吞吐量。
## 开发模式选型：代码级状态机 vs 低代码平台

* **低代码可视化平台（Dify / Coze）**：通过拖拽 UI 节点（如知识库检索、LLM 节点、条件分支）快速构建主流 RAG 提示链与轻量 Agent，极其适合快速原型验证（MVP）与中轻度业务的商业交付。
* **代码级框架（LangGraph / LlamaIndex Workflows）**：当智能体面临多轮循环 ReAct 调度、复杂的双向状态更新（Stateful）、并发执行冲突以及高度定制的异常流时，必须使用 Python 原生编写状态机进行精细的代码级控制。

**Agent 框架（Agent Frameworks）** 负责定义 Agent 的思考逻辑、状态转化以及工具管理的代码库：

- **LangChain / LangGraph**：目前最流行的大模型开发框架之一。开发者用它定义可调用的工具（使用 `@tool` 装饰器），LangGraph 负责管理工具调用的状态循环，解析模型返回的 JSON 并自动触发对应的 Python 函数。
    
- **Microsoft AutoGen**：微软推出的多智能体协作框架。允许定义多个具备特定工具调用能力的 Agent（如 `CodeExecutorAgent`），并在它们之间自动流转任务与工具执行。
    
- **CrewAI**：以“角色团队”为核心的 Agent 框架。开发者为不同的 Agent 分配具体角色和工具（例如“数据检索员”绑定 Google Search 工具，“报告撰写员”绑定 Markdown 生成工具），框架自动协调调起逻辑。
    

**应用程序后端（Application Backend）** 真正运行在服务器上、保存 API Key 并发起实际物理网络请求或数据库操作的代码环境：

- **FastAPI / Express.js 自研后端**：开发者自己编写的 Web 服务器。当后端收到大模型返回的 `{"name": "get_weather", "city": "上海"}` 时，后端的 Python/Node.js 代码会调用 `requests.get("[https://api.weather.com/](https://api.weather.com/)...")` 真实发起 HTTP 请求，拿到数据后再回传给模型。
    
- **Dify / Coze 等 Agent 平台后端**：可视化 agent 平台背后的微服务架构。当用户在前端界面点击运行或触发工具节点时，平台的后端引擎（通常由 Python/Go 编写）会在服务器的 Docker 容器或无服务器函数（Serverless）中运行 API 调用或代码片段。

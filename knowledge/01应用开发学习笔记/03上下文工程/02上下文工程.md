## 1. 核心概念与基础认知

### 1.1 Context 与 Context Window 的本质
* **Context（上下文）**：指大模型在单次决策或回答中所接收到的所有输入信息的总和。在工程意义上，它代表了影响模型当前决策的所有信息集合，包括：
  * 用户初始提问与指令（Prompt）
  * 背景信息与参考资料（知识库/文档）
  * 多轮对话历史记录
  * 可用工具与技能规范列表（Tools / Skills Specifications）
  * 工具执行结果与环境反馈（Tool Outputs / Environment Observations）
  * 系统级规则与安全约束（System Instructions / Rules）
  * 多智能体（Multi-Agent）间传递的结构化数据与中间产物
* **Context Window（上下文窗口）**：指大模型单次输入能够包含的最大容量上限，通常以 Token 为计量单位。
* **Token 计量标准**：文本拆分的最小单位。1 Token 约等于 0.75 个英文单词，或约等于 1.5 个汉字。
优秀的上下文工程能够极大降低 Token 耗用并提高系统稳定性。它通常包括：

- 定义代理行为和能力的系统提示语。
- 指导决策的任务约束条件。
- 工具调用的详细描述，明确说明何时及如何触发工具。
- 内存管理机制，专门用于跟踪多步骤执行中的状态变化。
- 稳健运行的错误处理与异常恢复模式。
### 1.2 主流大模型 Context Window 容量对比
* **Gemini 2.5 Pro**：100 万 Token（约合 7 本书的文本量，具备超长上下文处理能力）
* **GPT-5**：40 万 Token
* **Claude 4**：20 万 Token
* **DeepSeek V3**：12.8 万 Token
* **小型/成本优化模型**：通常仅几万 Token（无法装下数百页的技术手册或复杂数据）

### 1.3 粗暴全量投喂资料的三大现实限制
即便面对拥有百万 Token 窗口的模型，直接将所有原始文档或上下文全量塞给模型依然不可行，主要受制于以下三重限制：
* **窗口容量绝对限制**：大部分性价比高的小模型或中型模型窗口容量有限，装不下庞大的产品手册或代码库。
* **输入杂乱严重干扰模型理解与注意力**：未加精选的信息包含大量冗余、噪点甚至潜在矛盾。信息一多会导致大模型注意力分散、混淆重点，最终输出含糊其辞或产生幻觉。
* **API 调用成本呈指数级上升**：大模型采用 Token 计费模式。无节制塞入海量上下文会导致 API 调用开销急剧增加，严重影响大规模商业化落地的经济性。

## 2. Context Engineering 的定义与爆发背景

### 2.1 核心定义
Context Engineering（上下文工程）是指对大模型的输入内容（Context）进行精心设计、挑选、压缩、组织与管理的工程方法体系。
* **核心哲学**：“不改变模型本身的结构与参数，只改变模型所能看到的视野”。
* **终极目标**：在有限的 Context Window 限制下，让模型理解得更准、答得更好、消耗的 Token 更少。

### 2.2 三代 AI 工程重心的演进逻辑
* **Prompt Engineering（提示词工程）**：关注“怎么问问题/怎么把话说清楚”，解决表达问题。通过调整指令、角色与样例，塑造局部概率空间，激发模型已有能力。局限：无法凭空弥补缺失的外部知识与管理复杂状态。
* **Context Engineering（上下文工程）**：关注“怎么给信息/怎么给对信息”，解决输入环境与知识供给问题。研究如何在合适的时机，把最正确、最相关的上下文送入模型。局限：只解决输入侧供给，无法监督连续执行过程中的跑偏。
* **Harness Engineering（驾驭工程）**：关注“怎么搭建运行系统/怎么持续做对”，解决全流程持续执行与监督纠偏问题。
* **三者关系**：Prompt 是 Context 的一部分，Context 是 Harness 的一部分，系统边界与研究范畴依次递进扩展。

### 2.3 行业爆发的两大驱动力
* **模型基础推理能力达标**：现在的旗舰大模型能力已足够强大。大部分情况下回答质量差，并非模型不聪明，而是人类没有提供清晰、完整、结构化且重点突出的上下文。
* **AI Agent 范式的普及**：Agent 将大模型与外部工具相结合，在多轮交互中会频繁产生工具说明、调用参数与执行结果。长链路运行会导致 Context Window 被快速填满，Context 治理的优劣直接决定了 Agent 的成败。

## 3. Context Engineering 四大核心策略框架（基于 LangChain 体系）

### 3.1 保存 Context（Save / Persist Context）
* **核心原理**：将筛选总结后的上下文持久化存储于外部存储介质（如内存、数据库、磁盘文件），在模型后续请求需要时精确调取。
* **解决痛点**：解决跨会话持久化与长时记忆丢失问题，避免重复传输冗余信息。
* **典型案例**：ChatGPT 的 Memory 功能。当用户提及个人姓名、频道主题或偏好时，系统自动识别并持久化存储至 Memory 记忆库，在未来对话中自动装载。

### 3.2 选择 Context（Select Context）
从海量信息与历史库中，精准挑选与当前任务最相关的切片装载进 Context Window。

#### 静态选择（Static Selection）
* **原理**：将最核心、永远重要、必须严格遵守的规则与规范，在每次请求时全部强制硬编码放入 Context。
* **策略**：“全都要”，只要确保总容量不撑爆 Context Window。
* **典型案例**：Cursor 的 `.cursorrules` 文件、Claude Code 的 `CLAUDE.md` 文件（定义项目架构、编码范式与规范）。

#### 动态选择（Dynamic Selection）
* **原理**：根据用户当前输入，通过算法实时精准筛选关联度最高的信息送入 Context。
* **典型案例**：
  * **RAG（检索增强生成）**：对文档进行切块与向量化，根据用户提问动态检索 Top-K 最相关的切片。
  * **记忆与工具动态调取**：从数十甚至数百个工具中，根据当前意图仅动态挑选最相关的少数工具（如 3 个）注入 Context。

#### 高级实践：渐进式披露（Progressive Disclosure）与 Agent Skills
* **痛点**：若一次性将十几套复杂工具的详细说明、参数定义与 SOP 全部塞入 Context，会导致上下文窗口被挤爆，模型注意力大幅分散。
* **解法**：初始阶段仅暴露最少量的工具元信息（名称与简短描述）；当模型决定触发某种能力时，再按需下钻，动态加载具体的 SOP 规范、参考文档与执行脚本。

### 3.3 压缩 Context（Compress Context）
* **核心原理**：针对 Agent 运行过程中产生的大量历史对话、中间思考链与工具输出文本，定期进行提炼摘要并丢弃原始冗余文本，释放上下文空间。
* **解决痛点**：防止历史工具执行结果（如读取代码、网页抓取结果）迅速挤爆 Context Window。
* **典型案例**：
  * **Claude Code 的 auto-compact 机制**：当上下文使用率达到 95% 时，系统自动触发压缩程序，将前面的交互历史总结为简短摘要并清空原始明细。同时支持在 `CLAUDE.md` 中自定义压缩偏好（如优先保留测试输出与代码修改记录）。
  * **深度延伸（Context Reset / 上下文重置）**：Anthropic 实践指出，在长任务中单纯压缩仍可能残留“上下文焦虑”与历史负荷。更彻底的方案是直接重置 Context，启动一个干净上下文的新 Agent 进程并交接最新状态。

### 3.4 隔离 Context（Isolate Context）
* **核心原理**：在 Multi-Agent（多智能体）系统架构中，为不同功能模块的 Agent 设立互相隔离的上下文空间，实现职责分离与上下文解耦，避免信息交叉污染与上下文爆炸。
* **典型案例**：
  * **Anthropic 多智能体研究架构**：由 Lead Agent 充当总指挥官（负责任务拆解下发与总结），下设独立的 Sub-Agents（如专门负责 PDF 搜索、网络搜索、图片搜索的 Sub-Agent）。每个 Sub-Agent 拥有独立的工具集、运行历史与上下文空间，互不干扰。
  * **Claude Code 的 Sub-Agent 机制**：针对独立专项任务开启子 Agent 执行，保持主上下文干净。

## 4. 生产级工程中的 Context 治理实践

### 4.1 OpenAI 100 万行代码实验中的上下文治理
OpenAI 在无手写代码构建百万行生产级应用的实验中，总结了关键的上下文治理方案：
* **AGENTS.md 目录化重构**：早期将所有规范填入单一的庞大 `AGENTS.md`，导致信息过载与文件腐化。后来将其精简为仅 100 行左右的“目录索引页”，具体规范分散到子文件夹，由 Agent 按照渐进式披露原则下钻读取。
* **单一事实来源（Single Source of Truth）**：强制将散落在聊天软件、文档工具或员工大脑中的技术决策与约定全部沉淀进代码仓库，确保仓库是 Agent 能够感知的唯一上下文事实来源。

### 4.2 Cognition 与 LangChain 的思考
* **Cognition（*Don't build multi-agents*）**：指出无序的并发 Multi-Agent 极易引发上下文混乱与相互干扰，主张通过串行执行架构并结合严谨的 Context Engineering 来控制输入质量。
* **LangChain 范式**：强调上下文治理是智能体从“不可靠玩具”迈向“生产级应用”的基石。

## 5. 总结与核心结论

* **本质**：Context Engineering 是对大模型输入信息的供给侧改革。
* **原则**：上下文并非越多越好，而是“按需供给、分层结构化、在正确的时机给到最精准的信息”。
* **价值**：它是打造高成功率、低成本、稳定可控的 AI Agent 与智能化系统的必经之路。



## 上下文缓存（Hash Caching）

在构建大型 Agent 系统或高频调用的应用中，静态不变的系统指令、Few-Shot 范例或上万字的参考文档会在每次 API 调用中重复计费并增加延迟。 通过在 API 层面将这部分静态信息进行 Hash 锁定缓存，相同哈希的上下文在连续请求中直接重用，可降低近 80% 的 Token 成本，并显著拉低首 Token 延迟（TTFT），极大地提升了用户体验。

## 动态控制流与提示链（Prompt Chaining）

复杂的任务往往不能通过单次 Prompt 交互一蹴而就，应当将其拆解为多个子节点，通过代码或工作流进行链式流控（Prompt Chaining）。 提示链的核心逻辑是通过程序将前一个 LLM 节点的输出，执行转换、提取或多阶段处理后，作为下一个节点的输入，直到达到期望的最终结果。 典型场景如：

- 提示一：负责接收用户的输入，并从海量原始文档中检索出最相关的精准引文。
- 提示二：将提示一抽取的引文和原始文档共同作为输入，合成最终符合规范的问答结果。

## 历史对话截断与剪枝（Context Pruning）

由于大模型上下文窗口受限，长对话系统在运行中极易发生超限和模型注意力漂移。 解决该工程硬伤的常规手段是在工作流中引入历史记录总结或剪枝节点：

- 固定轮数截断：在状态更新中只保留最近 5 轮的历史对话轨迹，直接丢弃超期历史。
- 摘要压缩：调用一个低成本的小模型将久远的历史对话进行滚动式的提炼和摘要压缩，仅将摘要信息作为上下文传入主模型，实现上下文精简。

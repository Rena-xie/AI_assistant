## 一、 核心定义与工程演进

### 1. 概念与核心公式
* **定义**：Harness 原意为“马具”（缰绳、头套等约束装置）。在 AI Agent 系统中，Harness 指底座大模型之外，用于控制、监督、约束与驱动模型持续正确运行的整个外部系统环境与工程机制。
* **核心公式**：
  * Agent = Model + Harness
  * 一个完整 AI Agent 除去底层大模型本身，所有决定系统能否稳定、持续、正确交付结果的组件与机制统称为 Harness。
* **包含范畴**：系统规范规则（如 CLAUDE.md、AGENTS.md）、工具接口与调度、权限与隔离环境、执行编排、记忆与状态管理、自动化测试、闭环校验与失败恢复等。

### 2. AI 工程重心的三次演进
AI 领域的工程落地经历了从关注个体提示词到全局系统设计的三个阶段：
* **Prompt Engineering（提示词工程）**：关注“怎么问问题/怎么表达”。通过角色设定、格式约束与示例引导塑造局部概率空间。缺点是无法弥补缺失的外部知识，也无法管理复杂长链路的状态。
* **Context Engineering（上下文工程）**：关注“怎么给信息”。研究在有限上下文窗口内，如何按需、分层、动态地把最合适的信息送入模型视野。缺点是主要解决输入侧供给，无法监督模型连续行动过程中的偏航。
* **Harness Engineering（驾驭工程）**：关注“怎么搭建运行系统/怎么持续做对”。研究如何围绕模型构建监控、纠偏、校验与恢复机制，确保模型在长链路真实场景中稳定交付。

## 二、 成熟 Harness Engineering 的六层架构

### 1. 上下文边界管理
* 明确“我是谁”、“任务目标”及“成功验收标准”。
* 坚持相关性优先，进行信息裁剪，避免过载导致模型遗忘与注意力分散。
* 结构化组织信息，清晰划分规则、当前任务、运行状态与外部证据的物理分层。

### 2. 工具系统
* **工具按需供给**：避免工具过少导致能力不足，或过多导致乱用。
* **调用时机控制**：明确何时触发工具，防止无谓查询或应答偏航。
* **结果提炼与过滤**：工具返回的原始数据经过提炼筛选后再喂回模型上下文，保持高度相关。

### 3. 执行编排
* 为长链路任务提供轨道：理解目标 -> 判断信息完整度 -> 逐步分析 -> 生成阶段性输出 -> 检查与纠偏。
* 避免模型“想到哪做到哪”或交出半成品。

### 4. 记忆与状态管理
* 避免多轮交互中出现“失忆”或混乱。
* **状态三分类**：当前任务状态（Task State）、会话中间产物（Session Artifacts）、长期记忆与用户偏好（Long-term Memory）。

### 5. 评估与观测
* 建立独立客观的评价能力，解决 Agent“自我感觉良好”盲区。
* 包含输出验收环境验证、自动化测试日志、Trace/Metrics 指标监控及错误归因分析。

### 6. 约束校验与失败恢复
* **约束（Guardrails）**：定义明确的边界（哪些可做，哪些拦截）。
* **校验（Verification）**：输出前后的结构、逻辑与功能性自动检查。
* **恢复（Recovery）**：失败后的重试、降级策略、切环境与状态回滚。

## 三、 头部大厂的 Harness 最佳实践

### 1. OpenAI 的生产级 Harness 实践（100万行代码实验）
在 2025 年 8 月的内部实验中，OpenAI 依靠 3-7 人的工程师团队，驱动 Agent 在 5 个月内从零构建了近 100 万行代码的生产级应用，100% 代码由 AI 生成，研发效率提高至纯人工的 10 倍。

#### 核心优化维度：
* **上下文管理**：
  * 将早期臃肿的 AGENTS.md 瘦身至 100 行左右的目录索引，子规范分散在对应文件夹中按需读取（渐进式披露）。
  * 强制将散落在聊天记录、文档或员工脑中的技术决策搬入代码仓库，保持仓库为“单一事实来源（Single Source of Truth）”。
* **验证与反馈闭环**：
  * 集成 Chrome DevTools，让 Agent 能够自行截图、读取 DOM、模拟用户交互以自主验证 UI 并修复 Bug。
  * 接入日志与指标栈，任务跑在独立的隔离沙箱中，支持服务启动耗时等量化性能调优。
  * 制定严格的分层架构依赖规则，自动运行 Linter 和测试，将报错与修复建议重新反馈回上下文，形成无人值守的自动修复闭环。
* **技术债自动化清理**：
  * 设置后台 Codex 定期任务，扫描重构偏离架构规范的代码。
  * 后台任务自动扫描文档库，修正与代码不符的过时文档。
* **范式转移**：从“人类写代码”转变为 Human Steer, Agents Execute（人类掌舵，Agent 执行）。工程师的核心职责重塑为为 Agent 搭建稳定可靠的 Harness 系统环境。

### 2. Anthropic 的长任务 Harness 实践

#### 解决两大核心问题：
* **上下文焦虑（Context Anxiety）**：长任务运行后期上下文变满，模型因急于收尾而出现质量滑坡。Anthropic 采用 Context Reset（上下文重置）机制，直接重启全新干净进程并交接当前状态，彻底消除负担感。
* **自评失真（Self-Evaluation Distortion）**：Agent 既当开发者又当裁判容易过于乐观。采用生产与验收分离架构（Full Harness）：
  * **Planner**：将模糊自然语言需求拆解扩展为具体的功能列表。
  * **Generator**：逐项实现功能点，并与 Evaluator 协商交付标准。
  * **Evaluator**：独立的 QA 角色，真实操作页面与测试交互，不通过则打回重修。
* **效果数据**：对比单 Agent 模式（Solo：20分钟，$9，Bug遍地不可用），Full Harness 架构（6小时，$200）产出了高可用度、逻辑严密的产品。
* **随模型能力的动态调整**：随着模型（如 Claude 3.5 / Opus 4.6）全局统筹能力增强，早期强制逐项执行与频繁微观评估的限制可逐步放宽，Harness 呈现轻量化与粗粒度化演进。
